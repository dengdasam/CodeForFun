雪花WMS 系统校验与告警规范

版本 V1.0 适用范围 雪花 WMS（入出库、盘点、翻包、拆组垛、库存、接口） 技术栈 HZERO + Java + OceanBase(MySQL) 状态 待评审
这份规范要解决什么
版本迭代中校验逻辑与提示文案不断堆积，最终演变为：同一类错误在不同页面文案不一致、有的地方拦有的地方不拦、PDA 上报错看不懂、跨系统差异无人告警。本规范通过「校验分层 + 规则编码 + 统一结果模型 + 三级分级 + 告警治理」五件套，把校验与提示从散落的 if-else 变成可登记、可测试、可追溯、可运营的体系。

1. 总则与核心原则

1.1 术语定义

术语定义
校验（Validation）对输入数据、业务状态、关联关系、跨系统一致性进行检查并给出结论的过程
提示（Feedback）把校验结论反馈给当前操作用户的界面行为（弹窗、Toast、红字、声音等）
告警（Alert）系统检测到需要人员介入处理的异常，主动推送到告警渠道（企微、短信、邮件）
级别（Level）校验结论的严重程度：阻断 / 警告 / 提示
规则（Rule）一条可被独立登记、独立测试、独立复用的校验逻辑单元，拥有唯一规则编码
提示 ≠ 告警（务必区分）
提示是同步的、面向个人的、操作级的 —— "你这一次扫描错了"。
告警是异步的、面向组织的、系统级的 —— "这个仓库的库存与下游系统对不上了，需要人来查"。
二者对象、时机、渠道、处理方式完全不同，不允许混用同一套机制。

1.2 五条核心原则

原则含义违反的典型后果
① 统一出口所有校验结论必须经由统一结果模型返回，禁止各模块自行拼 String 或裸抛异常前端无法统一处理错误，文案与级别不可控
② 规则登记每条校验规则必须有唯一编码、登记台账、可关联测试用例规则不可追溯，测试覆盖率无法量化
③ 后端为王前端校验只为体验优化，后端必须独立完整校验，前端可绕过绕过页面的接口调用可写入脏数据
④ 分级响应校验结论必须明确级别，不同级别对应不同的表现形式与后续流程所有错误都做成弹窗，用户疲劳后盲点"确定"
⑤ 告警可行动每条告警必须回答「谁、做什么、不做的后果」；不可行动的告警一律降级或删除告警风暴，真正的问题被淹没

2. 校验体系：四层模型

所有校验按校验对象归入四层，每层职责单一、实现手段固定。禁止跨层混写（例如把"库存是否充足"写在 Controller 里做格式判断）。

L1
数据格式校验
必填·类型·长度
范围·枚举·正则
L2
业务规则校验
状态流转·数量逻辑
效期·批次·配额
L3
关联一致性校验
主数据存在性
单据上下游·库存账实
L4
外部对账校验
跨系统一致性
接口结果校验
四层自上而下串行通过，任一层产出「阻断」即终止流程

2.1 各层职责与实现手段

层级校验对象典型规则示例推荐实现手段执行位置
L1 数据格式 单个字段本身 箱码不能为空且符合 18~32 位编码规则；入库数量必须 > 0；日期格式合法；单位必须在值集内 Jakarta Bean Validation（@NotBlank / @Pattern / @DecimalMin） + 自定义约束注解 Controller 入参 / DTO
L2 业务规则 单据内部逻辑与状态 入库数量不得超过订单剩余量；已完结单据不可再修改；出库不得超可用库存；盘点单存在未处理暂挂行时不可完结 Specification 模式 + 状态机守卫 Domain Service
L3 关联一致性 跨实体、跨主数据 箱码必须存在于箱码主数据；托盘与箱码归属关系必须一致；物料必须在 WMS 物料表存在且启用；库位必须属于当前仓库 领域查询 + 断言，结果进入统一结果模型 Domain Service
L4 外部对账 跨系统、异步 WMS 净数与 OCMS 净数一致性；STTS 返回的箱数与实物扫码数一致；ERP 出库单据回执状态一致 定时任务 + 差异记录表 + 告警 Job / 异步对账
关于 L4
L4 与前三层最大的不同在于：它无法在操作时同步拦截。例如 WMS 与 OCMS 的净数差异，往往在单据完成后才暴露。因此 L4 必须落地为定时对账任务 + 差异结果表 + 告警推送，而不是指望在业务操作时拦住。这正是历史「1096 净数差异」需要投入大量人力逐单排查的根因——缺少常态化对账与差异告警。

2.2 校验时机

时机触发点典型校验说明
即时校验单个字段失焦 / 扫码枪回车箱码格式、箱码是否存在、物料一致性PDA 场景的主要校验方式，要求响应 < 500ms
提交校验点击【提交】/【确认】全部 L1~L3 规则、单据级完整性收集全部错误一次性返回，不做快速失败
过账校验单据状态流转（如完结、审批）状态合法性、下游依赖已满足由状态机守卫统一判断
异步校验定时任务 / 消息队列消费跨系统对账、超时未处理单据扫描产出告警，不阻塞前台操作

2.3 不可绕过原则

  • 所有写操作接口必须在服务端完成 L1~L3 全量校验，前端校验不得作为唯一依据。
  • 批量接口（Excel 导入、批量扫描、消息消费）同样执行全量校验，不得因为"数据是内部产生的"而省略。
  • 数据层补充兜底约束：唯一索引、非空约束、外键、库存不可为负的检查约束。应用层校验是用户体验，数据层约束是最后防线。
-- 兜底约束示例：确保同一单据同一行同一差异类型不重复记账，库存数量不为负
ALTER TABLE xhinv_difference_record
  ADD CONSTRAINT uk_diff UNIQUE (source_bill_code, source_line_num, difference_type,
                                 org_id, owner_id, warehouse_id, wharea_id,
                                 location_id, goods_id, batch_id, tenant_id);

ALTER TABLE xhinv_onhand_qty
  ADD CONSTRAINT chk_qty_non_negative CHECK (onhand_qty >= 0);

4. 统一结果模型

所有校验结论统一由 ValidateResult 承载，禁止各模块自行构造异常文案或返回裸字符串。

4.1 数据结构定义

/**
 * 统一校验结果对象
 */
public class ValidateResult implements Serializable {

    /** 是否全部通过（无任何 BLOCK 级错误） */
    private boolean passed;

    /** 错误明细列表，批量场景可包含多条 */
    private List<ValidateError> errors = new ArrayList<>();

    public static ValidateResult ok() {
        return new ValidateResult(true, Collections.emptyList());
    }

    /** 快速失败：产出一条阻断错误 */
    public static ValidateResult block(String code, String message) {
        return ValidateResult.block(code, null, message, null);
    }

    public static ValidateResult block(String code, String field, String message, String suggestion) {
        return single(ErrorLevel.BLOCK, code, field, message, suggestion);
    }

    /** 警告：不阻断，需二次确认 */
    public static ValidateResult warn(String code, String field, String message, String suggestion) {
        return single(ErrorLevel.WARN, code, field, message, suggestion);
    }

    /** 收集器模式：批量场景收集全部错误，不做快速失败 */
    public static ValidateResult collector() {
        return new ValidateResult(false, new ArrayList<>());
    }

    public ValidateResult add(ErrorLevel level, String code, String field, String message, String suggestion) {
        this.errors.add(new ValidateError(level, code, field, message, suggestion));
        this.passed = this.errors.stream().noneMatch(e -> e.getLevel() == ErrorLevel.BLOCK);
        return this;
    }
}

/**
 * 单条校验错误
 */
public class ValidateError implements Serializable {
    private ErrorLevel level;    // BLOCK / WARN / INFO
    private String code;         // WMS-IN-003
    private String field;        // 定位字段，如 qty
    private String message;      // 面向用户的错误描述
    private String suggestion;   // 处理建议
}

public enum ErrorLevel {
    BLOCK,   // 阻断：必须处理后才能继续
    WARN,    // 警告：二次确认后可强制继续，需留痕
    INFO     // 提示：仅信息反馈，不阻断流程
}

4.2 错误码体系

错误码与校验规则编码同号（一套编码，两个用途），避免"异常码"与"规则码"两套体系对不上。

构成说明示例
系统前缀固定 WMSWMS
模块码见 3.1 模块码表IN
序号三位数字，模块内递增，一经分配不可复用003
错误文案不要写死在代码里
错误码对应的文案、级别、处理建议统一维护在错误码字典中（可用 HZERO 消息/多语言能力或独立字典表 xhinv_error_code），代码里只引用错误码 + 动态参数。好处：改文案不用改代码和重新发版；可支持多语言；可做统一审计。 
-- 建议配套的错误码字典表结构（示意）
CREATE TABLE xhinv_error_code (
  id            bigint NOT NULL AUTO_INCREMENT,
  error_code    varchar(64)  NOT NULL COMMENT '错误码，如 WMS-IN-003',
  module_code   varchar(32)  NOT NULL COMMENT '模块码',
  level         varchar(16)  NOT NULL COMMENT 'BLOCK/WARN/INFO',
  message_tpl   varchar(500) NOT NULL COMMENT '文案模板，含 {0} {1} 占位符',
  suggestion    varchar(500) COMMENT '处理建议',
  owner         varchar(64)  COMMENT '规则负责人',
  source_ver    varchar(64)  COMMENT '来源需求/版本',
  status        varchar(16)  NOT NULL DEFAULT 'ACTIVE' COMMENT 'ACTIVE/DEPRECATED',
  tenant_id     bigint NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  UNIQUE KEY uk_code (error_code, tenant_id)
) COMMENT = '雪花-错误码字典表';

5. 提示规范与文案

5.1 三级分级定义

级别语义流程行为留痕要求
阻断 BLOCK 数据或业务不合法，继续会产生错误数据 流程终止，用户必须修正后重试 记录操作日志（谁、何时、被哪条规则拦下）
警告 WARN 存在风险或例外，但业务上允许继续 弹出确认框，用户显式确认后继续；部分场景需填写原因并触发审批 必须记录：操作人、确认时间、原因说明
提示 INFO 中性信息反馈，无需用户决策 流程正常继续 一般不记录，成功类操作除外

5.2 PC 端提示形态对照

级别首选形态适用位置消失方式
阻断字段级红字 + 顶部错误汇总条出错输入框正下方 + 表单顶部修正后自动消失
阻断模态对话框（Modal）全局性、无法定位到单一字段的错误点击【确定】
警告确认对话框（含【继续】【取消】）需要用户决策的例外用户选择后
提示Toast / Snackbar右下角或顶部居中3 秒自动消失
提示内联状态条结果区域常驻或下次操作消失
禁止的做法
  • 用 alert() 做业务提示。
  • 阻断级错误只用 Toast 轻描淡写飘过（用户会漏看）。
  • 批量操作逐条弹窗 100 次（必须收集全部错误一次性展示，支持点击跳转定位）。
  • 把技术异常栈直接展示给终端用户。

5.3 PDA / 移动端现场规范

现场环境噪音大、作业人员戴手套、屏幕小且距离远，提示必须多重感官冗余。

级别视觉听觉/触觉交互要求
阻断 红底白字，字号 ≥ 18sp，全屏或半屏 长蜂鸣（2 声）+ 长震动 必须提供可一键执行的下一步（如【重新扫描】【返回修改】），不要求用户记忆后再操作
警告 黄底黑字，字号 ≥ 16sp 短蜂鸣（1 声）+ 短震动 提供【继续】【取消】双按钮，按钮足够大（≥ 44dp 高）
提示 绿底白字 / 蓝底白字 单短响（成功音） 自动消失（2s），不阻塞连续扫码作业
PDA 特殊要求
连续扫码作业场景下，成功提示不能阻塞流程（不能用需要点击才能消失的弹窗），否则严重影响作业节拍。失败提示则必须中断并强制确认，防止作业人员未察觉错误继续扫下一箱。

5.4 文案三段式模板

模板：{发生了什么}（{实际值 → 期望值}）。{为什么不允许}。{下一步怎么做}。

变量占位：使用 {0} {1} 占位符，运行时填充真实数值，禁止拼接字符串
评价文案示例问题 / 优点
❌ 反例操作失败未说明失败原因、未给出处理路径
❌ 反例校验不通过无信息量，用户无法自助解决，必然提工单
❌ 反例库存不足缺关键数据：缺多少、哪个物料、怎么办
❌ 反例NullPointerException技术栈暴露给终端用户
✅ 正例物料 31A10000006000000（红爵8.5度330ml纤体听）当前可用 100 箱，本次需出库 120 箱，缺口 20 箱。出库量不得大于可用库存。请调整出库数量，或点击【强制出库】登记原因并提交审批。要素齐全：物料 + 数值对比 + 原因 + 两条处理路径
✅ 正例盘点单 PD20260808 尚有 3 行处于暂挂状态未录入结果。存在暂挂行时不允许完结。请先处理暂挂行，或登记延迟原因后再申请完结。定位明确，给出两条合规路径

文案编写检查清单

  • 是否包含具体数值（实际值 vs 期望值）？
  • 是否包含可定位标识（单据号 / 物料编码 / 箱码 / 库位）？
  • 是否说明了为什么不允许（业务规则本身）？
  • 是否给出了可立即执行的下一步？
  • 是否使用业务术语而非技术术语（不说"外键约束失败"，说"该物料尚未在 WMS 建档"）？

自定义约束示例（跨字段联动）

/**
 * 校验：净数不得大于毛数（L2，但也常作为字段联动校验前置）
 * 注意：PX03 库区不启用净数管理，此时毛数 = 净数允许相等放行
 */
@Target({TYPE}) @Retention(RUNTIME)
@Constraint(validatedBy = NetNotExceedGrossValidator.class)
public @interface NetNotExceedGross {
    String message() default "净数不得大于毛数";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class NetNotExceedGrossValidator
        implements ConstraintValidator<NetNotExceedGross, ReceiptScanCmd> {

    @Override
    public boolean isValid(ReceiptScanCmd cmd, ConstraintValidatorContext ctx) {
        if (cmd.getNetQty() == null || cmd.getGrossQty() == null) {
            return true; // 空值交给 @NotNull 处理，此处不重复报错
        }
        boolean pass = cmd.getNetQty().compareTo(cmd.getGrossQty()) <= 0;
        if (!pass) {
            ctx.disableDefaultConstraintViolation();
            ctx.buildConstraintViolationWithTemplate("WMS-STK-011")
               .addPropertyNode("netQty")
               .addConstraintViolation();
        }
        return pass;
    }
}

6.2 L2 规则层：Specification 模式 + 状态机

业务规则禁止写成一长串 if-else，应封装为可组合、可复用、可单测的 Specification 对象。

public interface Specification<T> {
    boolean isSatisfiedBy(T candidate);
    ValidateError error(T candidate);   // 不满足时产出标准化的 ValidateError

    default Specification<T> and(Specification<T> other) {
        return new AndSpecification<>(this, other);
    }
    default Specification<T> or(Specification<T> other) {
        return new OrSpecification<>(this, other);
    }
}

/** WMS-OUT-007 可用库存充足 */
public class StockEnoughSpec implements Specification<OutboundLine> {

    private final StockQueryService stockQuery;

    @Override
    public boolean isSatisfiedBy(OutboundLine line) {
        BigDecimal available = stockQuery.availableQty(
                line.getOrgId(), line.getWarehouseId(),
                line.getLocationId(), line.getSku(), line.getBatchId());
        return available.compareTo(line.getQty()) >= 0;
    }

    @Override
    public ValidateError error(OutboundLine line) {
        BigDecimal available = stockQuery.availableQty(...);
        BigDecimal gap = line.getQty().subtract(available);
        return new ValidateError(
                // 是否阻断由值集决定（见第 8 章）：有的组织允许强制出库（警告），有的严格阻断
                policy.levelOf("WMS-OUT-007", line.getOrgId()),
                "WMS-OUT-007", "qty",
                msg("WMS-OUT-007", line.getSku(), available, line.getQty(), gap),
                "请调整出库数量，或点击【强制出库】登记原因并提交审批。");
    }
}

/** WMS-STK-011 净数不得大于毛数 */
public class NetNotExceedGrossSpec implements Specification<StockLine> {
    @Override public boolean isSatisfiedBy(StockLine line) {
        return line.getNetQty().compareTo(line.getGrossQty()) <= 0;
    }
    @Override public ValidateError error(StockLine line) {
        return new ValidateError(ErrorLevel.BLOCK, "WMS-STK-011", "netQty",
            "物料 " + line.getSku() + " 毛数 " + line.getGrossQty()
              + " 小于净数 " + line.getNetQty() + "。净数（合格数）不得大于毛数（实物数）。",
            "请重新录入质检合格数，或修正毛数。");
    }
}

状态机守卫（替代散落的"当前状态不允许该操作"）

/**
 * 过账校验统一由状态机守卫：WMS-COM-020 非法状态流转
 */
@Component
public class CountOrderStateMachine {

    /** 状态流转白名单 */
    private static final Map<String, Set<String>> ALLOWED = Map.of(
        "DRAFT",      Set.of("COUNTING", "CANCELLED"),
        "COUNTING",   Set.of("RECHECKING", "SUSPENDED", "CLOSED"),
        "SUSPENDED",  Set.of("COUNTING", "CLOSED"),
        "RECHECKING", Set.of("FINISHED", "COUNTING"),
        "FINISHED",   Set.of("CLOSED")
    );

    public ValidateResult checkTransfer(CountOrder order, String targetStatus) {
        Set<String> allowed = ALLOWED.getOrDefault(order.getStatus(), Set.of());
        if (allowed.contains(targetStatus)) {
            return ValidateResult.ok();
        }
        return ValidateResult.block(
            "WMS-COM-020", "status",
            String.format("盘点单 %s 当前状态为【%s】，不允许变更为【%s】。",
                order.getOrderCode(), display(order.getStatus()), display(targetStatus)),
            "请返回列表刷新查看最新状态，或联系管理员处理。");
    }
}

6.3 校验编排：收集模式 + 责任链

/**
 * 提交校验编排：收集全部错误后一次性返回（禁止快速失败 + 逐条弹窗）
 */
@Service
public class OutboundSubmitValidator {

    private final List<Specification<OutboundOrder>> orderSpecs;   // 单据级规则
    private final List<Specification<OutboundLine>>  lineSpecs;    // 行级规则

    public ValidateResult validate(OutboundOrder order) {
        ValidateResult result = ValidateResult.collector();   // 收集模式

        // 单据级
        for (Specification<OutboundOrder> spec : orderSpecs) {
            if (!spec.isSatisfiedBy(order)) {
                result.add(spec.error(order));
            }
        }
        // 行级：携带行号定位，便于前端跳转到具体行
        for (OutboundLine line : order.getLines()) {
            for (Specification<OutboundLine> spec : lineSpecs) {
                if (!spec.isSatisfiedBy(line)) {
                    ValidateError e = spec.error(line);
                    // 附加行号，前端可渲染「第 3 行：xxx」并支持跳转
                    result.add(e.getLevel(), e.getCode(),
                               "lines[" + line.getLineNum() + "]." + e.getField(),
                               "第 " + line.getLineNum() + " 行：" + e.getMessage(),
                               e.getSuggestion());
                }
            }
        }
        return result;
    }
}

// Service 层统一出口
if (!result.isPassed()) {
    throw new WmsValidateException(result);   // 由全局异常处理器转为 400 Problem JSON
}
编排要点
  • 提交/批量场景用收集模式（collector()），一次性返回全部错误；即时校验用快速失败（单字段，立即反馈）。
  • 行级错误必须带行号定位（lines[3].qty），否则用户面对 100 行的错误列表无法下手。
  • 每个 Specification 独立单测，测试用例编号回填规则台账的「关联测试用例」字段。

告警设计红线
不可行动的告警 = 噪音。每条告警上线前必须回答三个问题：谁来处理？做什么？不做的后果是什么？回答不了任何一个，就降级为 P3 或删除。长期忽视告警会导致团队对告警脱敏，真正的 P0 也会被当成背景噪音。

8. 与配置治理衔接

本章承接《配置项治理》讨论，明确校验规则与配置项的关系——避免把校验本身做成新的配置项地狱。

内容应放在哪里反模式
校验规则逻辑代码（Specification / Validator）❌ 做成"表达式配置"，难调试难测试
阈值数值（如差异率预警线 5%）平台参数配置（可按层级覆盖）❌ 硬编码在代码里
适用范围（哪些组织/工厂启用该校验）值集（如 XHWINV.COUNT_NEW_MODE_ORG）❌ 每个工厂一个配置项
校验严格程度（阻断 or 警告）值集 + 默认级别，子节点只覆盖差异❌ 为"某工厂是否严格"单独建开关
文案与错误码错误码字典表（数据）❌ 写死在 Java 代码里
 
/**
 * 校验严格程度的分层解析（约定优于配置）
 *   1) 取全局默认级别（来自错误码字典）
 *   2) 按「组织 → 工厂 → 仓库」逐级查找覆盖值集，命中则用覆盖值
 *   3) 任何一层都未配置 → 用默认值
 *
 * 关键：覆盖值的载体是「值集里的一行数据」，而不是新增一个配置项。
 */
public ErrorLevel levelOf(String ruleCode, Long orgId, Long factoryId, Long warehouseId) {
    ErrorLevel level = errorCodeDict.getDefaultLevel(ruleCode);       // 默认
    level = overrideFrom(level, ruleCode, "ORG",      orgId);         // 组织覆盖
    level = overrideFrom(level, ruleCode, "FACTORY",  factoryId);     // 工厂覆盖
    level = overrideFrom(level, ruleCode, "WAREHOUSE", warehouseId);  // 仓库覆盖
    return level;
}
一句话总结
规则一个版本 + 适用范围数据化 + 阈值可配置 + 文案字典化。新增一个工厂时，只需在适用范围值集里加一行，而不是新增 N 个配置项或复制一份校验逻辑。
