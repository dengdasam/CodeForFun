02

Building Effective Agents：先判断该不该建

Anthropic
全文主论点：与数十个行业团队合作后的发现是——最成功的实现没有用复杂框架或专用库，而是用了简单、可组合的模式。只有能明确改善结果时，才增加复杂度。

01Workflow 与 Agent 的分界线

两者都属 agentic systems，但控制权的归属不同。这个区分决定了你后面所有设计工作的性质。
维度Workflow（工作流）Agent（智能体）
控制方式LLM 与工具由预定义代码路径编排LLM 动态决定自身流程与工具使用
任务路径开发者写定运行时生成，自主掌控完成方式
优势可预测、一致，适合定义清晰的任务灵活，模型驱动决策，可规模化
代价灵活性差延迟与成本高，错误会累积

02五种 Workflow 模式

这些模式不是规定性的，可以自由组合。原文建议先用单次 LLM 调用（加检索与示例）跑通，再逐步加层。
模式机制何时用
Prompt Chaining
提示链		固定顺序拆步，每次调用处理上一次输出；中间可加程序化校验（gate）任务能干净拆成固定子任务；以延迟换准确率
Routing
路由		先分类再导向专门化后续任务，避免为某类输入优化而损害其他类任务类别明显，且分类可由 LLM 或传统模型准确完成
Parallelization
并行化		切分（子任务并行）与投票（同一任务多次运行取多样输出）子任务可并行提速，或需多视角提高置信度
Orchestrator-Workers
编排者-工作者		中央 LLM 动态拆解、分派给 worker、综合结果无法预知需要哪些子任务（如改代码涉及多少文件）
Evaluator-Optimizer
评估者-优化者		一个生成、一个评估反馈，循环迭代存在明确评估标准，且迭代细化能带来可衡量收益

03Agent 循环与适用边界

实现本质通常只是「LLM 在循环里依据环境反馈使用工具」——从环境拿到 ground truth（工具结果、代码执行结果），在检查点或阻塞处暂停等待人类反馈，完成任务即终止，并设置最大迭代次数等停止条件。
判断要点
适用开放式问题、步骤数无法预测、无法硬编码固定路径；需要多轮运行，且对模型决策有一定信任
风险成本更高、错误会累积，应在沙箱中充分测试并设置护栏
两个高价值场景客户支持（对话+行动、成功标准清晰、可按成功解决计费）；编码 Agent（自动化测试可验证方案，但人工审查仍不可替代）
三条核心工程原则，以及「为工具做提示词工程」
  • 保持简单：agent 设计力求简洁；优先透明：显式展示规划步骤；精心打磨 ACI（Agent-Computer Interface）：靠充分的工具文档与测试。
  • 框架建议：先用 LLM API 直接实现（很多模式只需几行代码）；若用框架，务必理解底层代码——「对底层机制的误判是客户错误的常见来源」。
  • 工具定义要与主提示词同等投入：同一动作有多种表达（写 diff、重写整文件；代码放 markdown 或 JSON），软件工程里只是形式差异，对 LLM 难度却不同。
  • 格式三原则：给模型足够 token 先思考；格式贴近模型在互联网文本中自然见过的形态；避免精确统计上千行代码、字符串转义这类「格式开销」。
  • 防错设计（Poka-yoke）：构建 SWE-bench agent 时，优化工具所花时间多于优化整体提示词；把相对路径改成强制绝对路径后，模型使用无误。

→所有模式的地基：增强型 LLM（Augmented LLM）

上面五种 workflow 与 agent 都建立在同一前提上：每次 LLM 调用都已经叠加了检索、工具和记忆。当前模型能自己生成搜索词、选择工具、决定保留哪些信息——这是「agentic」真正的能力来源。
增强能力模型能自己做的事落地要点
检索生成搜索词、判断是否需要查资料按用例定制召回范围，而非接一个万能知识库
工具选择调用哪个工具、填参数接口要清晰、文档良好；MCP 是接入第三方工具生态的一条路径
记忆决定哪些信息保留到下一步与 12-Factor 的「拥有上下文窗口」直接对应

→决策树：什么情况下才往上加复杂度

1. 能不能用一次 LLM 调用解决？
   └─ 能 → 先做这一次调用，加入检索与上下文示例，多数应用到此为止
2. 这个任务换来的准确率提升，值不值额外的延迟与成本？
   └─ 不值 → 停在这一层
3. 任务路径能否预定义？
   └─ 能且要求稳定 → 选 Workflow（五种模式按需组合）
   └─ 不能、步骤数无法预测 → 才考虑 Agent
4. 上 Agent 前先确认：
   ├─ 有清晰的成功标准（可验证）
   ├─ 有反馈闭环（能拿到环境 ground truth）
   ├─ 有检查点/停止条件（最大迭代数、人工确认）
   └─ 已在沙箱中充分测试并设置护栏
原文反复强调：模式不是规定性的，可以组合；上生产时不要犹豫减少抽象层、回归基础组件。最成功的团队往往是用最简单方案、靠全面评估迭代出来的。
03

Demystifying evals：评测即需求，不是事后检查

Anthropic
核心主张：评测的价值会随 agent 生命周期复利增长，但成本前置、收益后置，因此最容易被低估和推迟。没有评测的团队困在「修好一个失败又制造另一个」的反应式循环里，分不清真实回归与噪声。

01术语表：评测的九个组件

先把语言统一，再谈方法论。尤其是 outcome 与 transcript 的区分——「agent 说已订好」不算，数据库里真有订单才算。
术语定义
task单个测试，含明确输入与成功标准
trial对同一 task 的一次尝试；因输出随机，需跑多次取一致结果
grader对某方面表现打分的逻辑；一个 task 可有多个 grader，每个含多个 assertion
transcript一次 trial 的完整记录：输出、工具调用、推理、中间结果
outcometrial 结束时环境的最终状态，而非 agent 的自述
evaluation harness端到端跑评测的基础设施：给指令与工具、并发跑、记录步骤、评分、聚合
agent harness让模型「成为 agent」的系统；评 agent 其实是评 harness + 模型的组合
evaluation suite一组 task，通常共享一个宽泛目标（如客服 suite 含退款、取消、升级）
evaluation给 AI 一个输入，用评分逻辑衡量输出是否成功；这里聚焦可自动化、无需真实用户的评测

02三类 Grader：为任务选对的，而非只用一种

类型方法优劣
Code-based
代码评分		字符串匹配、二元测试（fail-to-pass / pass-to-pass）、静态分析、outcome 验证、工具调用验证、transcript 分析快、便宜、客观、可复现；但对合法变体脆弱，难评主观任务
Model-based
模型评分		rubric 打分、自然语言断言、成对比较、参考答案对比、多 judge 共识灵活、能捕捉细微差别；但非确定性、更贵，需与人工校准
Human
人工评分		专家评审、众包、抽样检查、A/B、标注者一致性金标准质量；但贵、慢，主要用于校准模型评分器
Capability vs Regression：能力评测问「能做好什么」，期望通过率低（留出爬坡空间）；回归评测问「还保得住原来能做的吗」，期望通过率接近 100%。高通过率的能力评测可以「毕业」为持续运行的回归 suite。
非确定性：pass@k 是 k 次中至少一次成功的概率（随 k 上升）；pass^k 是 k 次全部成功的概率（随 k 下降）。单次 75% 跑 3 次全过 ≈ 42%。面向用户的 agent 应看 pass^k。

03从 0 到 1 的 8 步路线（三阶段）

阶段 A · 收集任务：Step 0 尽早开始（20–50 个来自真实失败的简单任务就够）→ Step 1 从已在手工测的东西开始（bug tracker、支持队列）→ Step 2 写无歧义任务 + 参考解（两个专家独立判断须得出相同 pass/fail；0% pass@100 通常是任务坏了）→ Step 3 构建均衡问题集（既测「该发生」也测「不该发生」，避免单边优化）。
阶段 B · 设计 harness 与 grader：Step 4 每次 trial 从干净环境开始，避免共享状态造成相关性失败或靠 git history 虚高成绩 → Step 5 优先确定性 grader，不要规定过细的步骤/工具调用顺序（「评它产出了什么，而不是它走了哪条路」），多组件任务给部分分，LLM judge 分维度独立打分并允许返回 Unknown。
阶段 C · 长期维护：Step 6 读 transcript（不读就不知道 grader 是否在工作，失败要「显得公平」）→ Step 7 监控 capability eval 饱和（100% 只追回归、不再提供改进信号）。
六种评测方法的分工：瑞士奶酪模型
  • Automated evals（离线）：迭代快、可每 commit 跑；但与真实使用不符时产生虚假信心，需持续维护防漂移。
  • Production monitoring（在线）：揭示规模化真实行为；但反应式、信号噪声大。
  • A/B testing（在线）：衡量真实用户结果；但慢、只测已部署改动、不知「为什么」变。
  • User feedback（在线）：暴露未预料问题；但稀疏、自选择、偏向严重问题。
  • Manual transcript review：建立失败模式直觉；但耗时、覆盖不一致。
  • Systematic human studies：多评分者金标准；但贵且慢，用于校准 LLM grader。
  • 结论：没有任何单层能拦住所有问题。最有效的团队 = 自动化评测做快速迭代 + 生产监控做 ground truth + 定期人工复核做校准。
最容易踩的坑（节选）
  • CORE-Bench 的反面教材：Opus 4.5 起初仅 42%——严格评分把 96.12 判错（期望 96.124991…）、任务规格含糊、随机性任务无法精确复现。修 bug + 放宽 scaffold 后升至 95%。
  • METR：任务要求优化到某阈值，评分却要求「超过」该阈值——遵守指令的模型反而被罚。
  • Opus 4.5 在 τ2-bench 订机票：发现政策漏洞，按评测算失败，但对用户是更优解——静态评测上限与创造性解法之间的张力。
  • 迟迟不建评测；任务不可解；单边评测；只测路径不测产物；无部分分；grader 可被绕过；LLM judge 未校准；trial 共享状态；不读 transcript；对饱和分数照单全收。

→按 agent 类型设计评测

基本功不变，但 grader 组合随 agent 类型而变。四类典型 agent 的评测重心：
类型独特挑战推荐 grader 组合代表基准
编码 Agent代码可自动化测试验证，但功能正确不等于符合系统需求确定性单测 + LLM rubric 评代码质量；可选静态分析、state check、tool callsSWE-bench Verified（一年内 40%→>80%）、Terminal-Bench
对话 Agent交互质量本身就是被评对象，成功是多维的以 model-based 为主：工单是否解决 + 轮数约束 + 语气 rubric，需第二个 LLM 模拟用户τ-Bench、τ²-Bench
研究 Agent「是否全面」专家有分歧；ground truth 随内容变化；输出越长越易错groundedness（论断有来源）+ coverage（关键事实齐全）+ source quality（来源权威）BrowseComp
Computer use通过截图/点击/键盘操作 GUI；DOM 快但耗 token，截图慢但省 tokenURL + 页面状态检查 + 后端状态验证（确认订单真下了，而非只看到确认页）WebArena、OSWorld
评测框架选型：六个候选，快速选一个契合工作流的
  • Harbor：容器化环境跑 agent，支持云端规模试验，标准化 task/grader 格式；Terminal-Bench 2.0 经其 registry 分发。
  • Braintrust：离线评测 + 生产可观测 + 实验追踪；autoevals 含事实性、相关性等预置打分器。
  • LangSmith：追踪、离线/在线评测、数据集管理，深度集成 LangChain。
  • Langfuse：自托管开源替代，适合有数据驻留要求的团队。
  • Arize：Phoenix（开源追踪/调试/评测）+ AX（SaaS 扩展规模、优化与监控）。
  • 作者的提醒：框架好坏取决于你喂给它的 task 与 grader 质量——把精力投在题目本身，而不是挑框架。
04

12-Factor Agents：生产级的工程约束

18.8k stars
总纲问题：「有哪些原则，能让我们构建真正好到可以交到生产客户手里的 LLM 软件？」作者的答案：好 agent 主要由软件构成，不是「给你一个 prompt、一袋工具，循环直到达成目标」。落地路径是把小颗粒度、模块化的 agent 概念渐进嵌入已有产品，而不是绿地重写。
#原则核心含义（中文整理）
01Natural Language to Tool Calls
自然语言转工具调用		最小原子操作：自然语言输入转成结构化 JSON；整个系统可视为「自然语言 → 结构化输出」管道
02Own your prompts
拥有自己的提示词		不用框架黑盒模板；prompt 像代码一样存在自己仓库，可版本化、diff、review、测试
03Own your context window
拥有自己的上下文窗口		上下文构造权归你；不被 role: user/assistant 限制，可用 XML、Markdown 等任意结构组织事件与状态
04Tools are just structured outputs
工具即结构化输出		工具调用本质就是模型输出的一段 JSON；拿到后执行的是普通代码，无需绑定框架抽象
05Unify execution state and business state
统一执行状态与业务状态		执行状态（第几步、等什么）不要藏在框架私有对象里，应与业务数据同处一处，便于观测、恢复、调试
06Launch/Pause/Resume with simple APIs
简单 API 启停恢复		必须支持启动 / 暂停 / 恢复，暂停可跨越几分钟到几天，等待人工审批或外部事件
07Contact humans with tool calls
用工具调用联系人类		人介入时建模成一种工具调用（如 request_human_input），而非特殊分支逻辑；人机交互也走统一状态机
08Own your control flow
拥有自己的控制流		循环、分支、重试、串并行、子 agent 编排由你的代码决定，不把决策权完全交给 LLM 自由循环
09Compact Errors into Context Window
把错误压缩回上下文		错误要压缩成简短结构化信息回灌，让模型自我修复；同时设重试上限，防死循环与上下文爆炸
10Small, Focused Agents
小而专注的 Agent		不造全能巨型 agent；拆成目标单一的小步骤，各自有明确工具集与上下文边界
11Trigger from anywhere, meet users where they are
随处触发，就地服务		不只从聊天框唤起；可被 cron、webhook、Slack、邮件、CI 任意事件触发，结果投递到用户所在处
12Make your agent a stateless reducer
无状态 reducer		写成纯函数式 (state, event) → newState / nextStep；不依赖内存隐式状态，从而可重放、可测试、可水平扩展
框架的 7 步失败循环（原文最尖锐的一段）
  • ① 决定做一个 agent → ② 产品设计、UX 映射、确定问题 → ③ 想快，抓一个 $FRAMEWORK 开干 → ④ 做到 70–80% 质量线 → ⑤ 意识到 80% 对面向客户的功能根本不够 → ⑥ 要突破必须逆向工程框架的 prompt、流程、内部机制 → ⑦ 推倒重来。
  • 根因：框架提供的抽象层级，与生产级所需的控制粒度不匹配；抽象一旦错误，代价是重写。
  • 元原则：即使 LLM 继续指数级变强，可靠性、可扩展性、可维护性仍来自工程技法，不来自模型能力。
  • 附录第 13 条：Pre-fetch all the context you might need——提前取好可能需要的上下文，减少运行时工具往返的成本与延迟。

→基线循环：理解 12 条原则的前提

作者说「agent 就是这个循环」。12 条原则本质上是在回答：这个循环里的每一步，哪些权必须握在你自己手里。
initial_event = {"message": "..."}
context = [initial_event]

while True:
    # 1. LLM 决定下一步，输出结构化 JSON（即 tool calling）
    next_step = await llm.determine_next_step(context)
    context.append(next_step)

    # 2. 判定完成
    if next_step.intent == "done":
        return next_step.final_answer

    # 3. 确定性代码执行工具调用
    result = await execute_step(next_step)

    # 4. 结果追加到上下文，进入下一轮
    context.append(result)
软件本身是一张有向图（DAG）。Agent 的许诺是「扔掉 DAG」——只给 LLM 图的边，让它实时决定节点，从而写更少代码、能自恢复。但作者明确判定：这条路在实际生产中并不成立，这正是 12 条原则存在的理由。

五种模式代码骨架

伪代码
把五种 workflow 模式写成最小伪代码，方便对照自己的业务流程选型。注意：控制流都写在代码里，LLM 只负责节点内的判断——这正是 12-Factor 的 Factor 08。
# 1. Prompt Chaining 提示链：固定顺序 + 中间校验
outline  = llm("写大纲", input)
assert validate(outline)              # gate：不通过就停/重试
draft    = llm("按大纲写正文", outline)
translated = llm("翻译", draft)

# 2. Routing 路由：先分类，再分流到专用提示词/工具
category = llm("分类", input, choices=["退款","技术支持","一般"])
result   = ROUTERS[category](input)   # 每类独立的提示词与工具集

# 3. Parallelization 并行化：切分 或 投票
parts = split(input)                  # 切分：各子任务并行
results = parallel([llm(p) for p in parts])
votes = [llm("审查漏洞", input) for _ in range(3)]   # 投票：多次独立运行
final = majority(votes)

# 4. Orchestrator-Workers 编排者-工作者：子任务由模型动态决定
plan = llm("拆解任务并分派", input)   # 子任务不是预先写死的
results = parallel([execute(t) for t in plan.tasks])
return llm("综合结果", results)

# 5. Evaluator-Optimizer 评估者-优化者：生成→评分→迭代
answer = llm("生成", input)
for i in range(MAX_ITER):             # 停止条件必备
    verdict = llm("按 rubric 评分", answer)
    if verdict.passed: break
    answer = llm("按反馈改写", {"answer":answer,"feedback":verdict})
return answer
关键区别：模式 4 与模式 3 的差异在于子任务是否预先定义；模式 5 的前提是存在明确的评估标准且迭代能带来可衡量收益——没有 rubric 就不要硬上评估者-优化者。

评测设计示例

好任务 vs 坏任务
维度坏任务（制造噪声）好任务（可验证）
规格明确性「写个脚本处理订单」但测试假定某个未说明的路径「读取 /data/orders.csv，输出按金额降序的前 10 行 JSON」
可判定性「回答要专业一点」——两个专家判断不一致「引用必须来自给定文档，且每个论断标注来源段落」
可解性0% pass@100 却归因于模型弱配参考解，先证明任务可解、grader 配置正确
方向均衡只测「该搜索时是否搜索」→ agent 什么都搜同时测「该搜」（查天气）与「不该搜」（谁创立 Apple）
部分分识别出问题但退款失败 = 完全失败识别问题+验证客户+退款失败 得 2/3 分，明显区别于一开始就失败
路径自由度强制特定工具调用顺序，惩罚合法新解法评最终 outcome，只在确有必要时检查 transcript

  state_check:                        # outcome 验证：数据库真实状态
    query: "SELECT status FROM orders WHERE id=42"
    expect: "paid"
  tool_calls:                         # transcript 分析：工具使用合规
    forbidden: [drop_table, direct_db_write]
  llm_rubric:                         # 模型评分：代码质量（分维度独立 judge）
    dimensions: [readability, minimal_change, test_coverage]
  tracked_metrics:                    # 成本与效率基线
    max_tokens: 8000
    max_turns: 12
实务建议：真实使用中通常只靠单测验正确性 + LLM rubric 评代码质量，其余按需加。不要一上来就堆满所有 grader。

→非确定性怎么看：pass@k 与 pass^k 的数值对照

单次成功率 pk=1pass@3（至少一次成功）pass^3（三次全成功）
75%75%1 − 0.25³ ≈ 98.4%0.75³ ≈ 42.2%
90%90%1 − 0.1³ ≈ 99.9%0.9³ ≈ 72.9%
50%50%1 − 0.5³ ≈ 87.5%0.5³ ≈ 12.5%
同样是「单次 50%」，pass@3 看起来有 87.5% 很好看，pass^3 却只有 12.5%。面向用户的 agent 要看 pass^k——用户期待的是每次都可靠，不是「多试几次总有一次对」。

12-Factor 逐条落地要点

检查 + 反模式
#落地动作反模式（要避免的）
01定义「自然语言 → 结构化 JSON」的最小原子调用让模型直接输出自由文本，再由代码猜意思
02prompt 放自有仓库，可 diff / review / 测试用框架黑盒模板，改一个词都要逆向工程
03用 XML/Markdown 自定义结构组织事件与状态被 user/assistant 消息数组绑死，状态塞不进上下文
04工具 = 结构化输出 + 普通代码执行依赖框架工具抽象，换框架就要重写全部工具
05执行状态与业务数据同表/同事件流状态存在框架内存对象里，进程重启即丢
06提供启动/暂停/恢复 API，支持跨天等待把长时间审批实现成轮询阻塞，占满连接
07request_human_input 建模成工具调用人工审批写成散落的 if-else 分支，无法审计
08循环、分支、重试、编排全部由代码控制把控制流完全交给 LLM 自由循环，无法设停止条件
09错误压缩成结构化摘要回灌，设重试上限把完整错误堆栈塞回上下文，越跑越长直到溢出
10拆成目标单一、工具集明确的小 agent造一个万能巨型 agent，上下文与权限都失控
11支持 cron/webhook/邮件/CI 触发，结果投递到用户处只能从聊天框唤起，嵌不进真实业务流程
12(state, event) → newState 纯函数 reducer依赖内存隐式状态，无法重放、无法水平扩展

AI 产品设计落地理念

从原则到判断
这些资源讲的是工程与评测，但落地时真正决定成败的是产品判断。以下八条理念是从原文结论中提炼、面向产品设计决策的「翻译层」——不是原文照搬，而是把工程约束翻译成 PM 每天要做的选择题。

01先问「该不该用 AI」，再问「怎么用 AI」

最成功的实现往往没用 agent。设计起点应是：这个任务用确定性代码能不能解决？能，就不用 AI；需要模糊匹配/语义理解/开放生成时才引入模型。AI 不是升级选项，是成本项——它带来延迟、不确定性和运维复杂度，必须换回明确价值。

02把「不确定性」设计成产品特性，而不是隐藏的 bug

传统产品追求「同样输入同样输出」，AI 产品必须接受输出波动。设计时要回答三件事：怎么让用户知道模型在犹豫（置信度/来源标注）、怎么让用户纠正（可编辑/可重试/可反馈）、怎么在失败时优雅降级（转人工/返回保守结果）。把不确定性暴露在交互层，而不是埋在后端祈祷它不发生。

03评测即需求：写不出评测，就是需求没想清楚

「回答要专业」「要理解用户意图」都不是需求——两个专家读这句话会得出不同的 pass/fail。把需求写成「95% 的输出在 rubric 上 ≥4/5」「引用必须标注来源段落」时，需求才真正定义完成。写评测任务的过程，就是消除规格歧义的过程。

04评结果，不评过程

不要规定 agent 必须走哪条路、先调哪个工具——那会让测试变脆、惩罚合法的新解法，还会让模型学会「按步骤演给你看」。定义清楚最终状态（outcome）和必要的护栏约束，把路径自由留给模型。你管边界，它管路径。

05渐进式授权：从「建议」到「代办」

用户对 AI 的信任是靠一次次正确累积的。产品设计上应设计权限阶梯：只读建议 → 用户确认后执行 → 低风险自动执行 → 高风险仍需确认。12-Factor 的「把人建模成工具调用」正是为此——审批不是特殊分支，而是状态机里的一个正常节点，可记录、可重放、可审计。

06失败要「显得公平」

评测里的失败必须让人一看就知道错在哪、为什么错。如果失败看起来莫名其妙，要么是任务规格含糊，要么是 grader 误杀了合法解。读 transcript 是产品经理的核心技能——不看运行轨迹，你分不清「模型错了」和「你的评测错了」，也就无法真正改进产品。

07成本与延迟是产品决策，不是技术细节

选大模型还是小模型、流式还是批量、要不要缓存——这些直接决定用户体验和毛利。PM 要建立心智模型：输入 token 便宜、输出贵 3–5 倍；高频低风险任务用小模型；长系统提示词启用缓存。把成本预算写进 PRD，就像写性能指标一样。

08评测体系是活资产，要有 owner

产品会变、模型会换、用户行为会漂移，评测套件必须像单元测试一样日常维护。最有效的组织模式：专职团队管基础设施，领域专家与 PM 贡献任务——让最贴近需求的人定义成功，而不是让算法团队替业务方拍板什么叫「好」。

产品设计示例详解

三个完整案例
以下三个示例从「需求 → 形态判断 → 交互设计 → 评测设计 → 工程约束」五个维度完整拆解，分别代表 workflow 型、RAG 型、agent 型三类最常见的 AI 产品。示例为教学用途的推演，用于演示如何把前面 18 章的原则用到具体设计上。

示例 1智能单据校验助手（Workflow 型）对应雪花 WMS 入库校验场景

业务问题：入库单据字段多、规则杂，人工校验耗时且易漏；规则本身是明确的（库位、批次、含瓶标记、下线即走判定）。
① 形态判断：规则明确 → 不走 agent，用 Prompt Chaining + Gate。但更准确地说：绝大多数校验规则应该直接写成代码（强校验固化的思路），只在「语义匹配」类环节（如物料名称模糊匹配）用模型。isShipUponPline 的取值分流用代码路由，不交给模型决定。
② 交互设计：校验结果分三档展示——✓ 通过 / ⚠ 需人工确认 / ✗ 阻断；每条结论附带命中的规则编号与原始字段值，可点击跳转；提供「一键修正建议」但必须人工确认后写入。
③ 评测设计：20–50 个来自真实历史差错的单据作为 task；grader 以 code-based 为主（字段比对、规则命中、DB 最终状态），LLM judge 只评「修正建议是否合理」；覆盖「该拦截」与「不该拦截」两类，避免误报率失控。
④ 工程约束：规则版本化落库（config_version_id 固化到单据），prompt 与规则分离；校验状态与业务单据同源存储，可在中断后重放；错误压缩成结构化摘要回灌，重试上限 3 次。
设计要点：这个产品的价值不在「AI 多聪明」，而在「规则可追溯 + 失败可解释」。把模型用在唯一需要语义判断的窄环节，其余全部确定性——这正是 12-Factor 说的「好 agent 主要由软件构成」。

示例 2企业知识库问答助手（RAG 型）最容易被做错的品类

业务问题：制度文档、操作手册、历史工单散落各处，员工找不到答案，重复提问占用大量时间。
① 形态判断：典型 RAG 场景——知识动态更新、私有、需要引用来源。不需要 agent 的自主规划；一次增强型 LLM 调用就够（检索 + 生成），只有复杂多跳问题才升级为 workflow。
② 交互设计：每个回答必须带可点击的引用来源（文档名 + 段落）；检索不到时明确说「未找到相关规定」并给出人工咨询入口，而不是编造；提供「这条回答是否有用」的轻量反馈，直接回流成评测任务。
③ 评测设计：三类 grader 组合——groundedness（每个论断有检索来源支撑）、coverage（必须包含的关键事实）、source quality（来源是否权威，而非只取第一个检索结果）；rubric 必须定期用专家人工判断校准。特别注意：别只测「能答对」，也要测「该说不知道时说不知道」。
④ 工程约束：检索与生成分离，可独立评估召回质量；上下文由自己构造（Factor 03），不依赖框架的消息数组；记录完整 transcript 供定期抽查，失败要能定位是「没检索到」还是「检索到了但没用好」。
设计要点：RAG 产品的质量上限主要由检索质量决定，不是生成质量。先把「找不找得到」做好，再优化措辞。用户信任来自「敢标来源、敢说不知道」。

示例 3数据分析 Agent（Agent 型）真正需要自主规划的品类

业务问题：业务人员提出自然语言问题（如「对比华东和华南上季度的退货率变化并归因」），系统需要自行决定查哪些表、怎么聚合、生成什么图表——步骤数无法预知。
① 形态判断：这类任务符合 agent 的三个前提：开放式、步骤数无法预测、无法硬编码路径。但需要严格护栏：数据库只读连接、查询超时、行数上限、禁止写操作。
② 交互设计：展示 agent 的执行计划（透明原则）——「我将查询订单表 → 关联退货表 → 按区域聚合」，用户可在执行前修改；长任务支持暂停/恢复；结论附数据快照与分析口径，可一键导出；关键动作（如导出大批量数据）需二次确认。
③ 评测设计：以 outcome 为主——最终数据结果是否正确（可用固定 SQL 比对）；辅以 tool_calls 检查（有没有越权查表）、transcript 约束（轮数与 token 上限）；用 pass^k 而非 pass@1 衡量可靠性，因为用户期待每次都对。
④ 工程约束：控制流由代码掌握，agent 只决定节点内动作（Factor 08）；执行状态与查询任务同表存储，支持跨天恢复（Factor 06）；工具集精简为「查表/聚合/画图」三个结构化输出（Factor 04）；错误压缩回灌并设重试上限（Factor 09）。
设计要点：这是三个示例里唯一真正需要 agent 的——因为路径确实无法预知。但越是 agent 型，越要把权限边界、停止条件、可审计性做扎实。自由度和约束力必须同步增长。
