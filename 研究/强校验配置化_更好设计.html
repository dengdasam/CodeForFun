强校验配置化的更好设计

契约即校验 · 编译即强制 · 边界即唯一 · 事件即版本 · 终局：校验器消失  ·  2026-11-26

本文解决什么。上一版回答"校验能不能配置化"；本文回答"怎样让强校验根本配不掉"，并在最后一章给出再深一层的终局——让非法状态根本无法构造，校验器随之消失。前 11 章是可直接落地的工程方案：契约目录、规则语法、10 条 WMS 规则、DMN 决策表、影子发布、CI 门禁、错误码资源表、排期与风险清单。

01

问题诊断：上一版的三个缺口

为什么升级

上一版（JSON Schema + 条件 DSL + 提示资源表 + 三端生成 + 三级管控）方向正确，但仍是运行时配置驱动，存在三个结构性缺口。

01DSL 会腐化成第二套代码

表现：x-condition 从一条简单条件起步，逐步长出嵌套判断、自定义函数、例外清单。
根因：DSL 本质上是一门语言，只要图灵完备度够用，业务就会不断往里塞逻辑。
后果：几年后它就是当初想消灭的硬编码，只是从 .java 挪到了 .json，而且没有 IDE 支持、没有单测、没有重构工具。

02三端生成本身成为新的维护面

表现：前端、后端、数据库各生成一份校验器，生成器要测、语义要对齐、版本要同步。
根因：复杂度没有消失，只是从"三份手写代码"转移成"一个生成器 + 三份产物 + 对齐测试"。
后果：新增一类校验要改生成器；生成器出 bug 三端同时中招；排查问题要多看一层生成逻辑。

03强校验分级靠人，不靠机制

表现："不可变规则禁止配置化""强校验双人审批"是流程约束，不是技术约束。
根因：运行时只要存在 enabled: true/false，就永远存在被配掉的可能。
后果：一次紧急上线、一次值班图省事，就能绕过审批。脏数据进系统后无法回溯是哪次配置改动导致的。
升级方向：把"强校验是否存在"从运行期挪到构建期。运行期不再有开关可配，只有参数可调——这是整套设计的分水岭。

设计总纲：四原则

逐条展开
原则具体做法解决什么
契约即校验规则内嵌在 Schema / DDL 注释 / Proto 选项中，与字段同处一处、同 PR 提交、同版本发布规则与字段模型漂移；DSL 另起炉灶
编译即强制强校验在构建期物化为校验器产物；产物中没有 enabled；要改必须改源码走 CI强校验被热关；三端生成器的维护负担
边界即唯一只在服务端 API 边界权威执行一次；前端从 OpenAPI 生成"体验提示"（不可信）；DB 保留最终硬约束三端语义不一致；绕过前端直调接口
事件即版本规则绑定业务事件（如"出库单创建"）版本；历史单据按发生当时的规则版本解释新规则误判老数据；规则演进无追溯
边界划分：强校验的存在性（是否存在、是否阻断）属于源码；强校验的参数（阈值、重试次数）可配置但带安全域；提示文案完全配置化、秒级热更新。三者走三条不同通道，互不越界。

架构对照：从解释器到编译器

链路变化

同一条规则（下线即走时产线必填）在两套设计里的生命周期完全不同：

上一版 · 运行期配置库写入 enabled:true

执行运行时解释 DSL
风险改配置即可关掉强校验

门禁CI 性质测试 + 评审
执行生成不可热改产物
结果要关必须发版 + 留痕
环节上一版更好设计

规则表达JSON Schema + x-condition DSLSchema 管结构 + DMN 决策表管业务联动（业务可读、命中可解释）

规则模型与契约语法

可执行定义

契约仓库按业务域分层，每个场景四类文件：字段契约、规则决策表、错误码资源、生成产物。

4.1 目录结构
contracts/
  wms/
    outbound/
      ship-upon-pline.schema.json     # 字段契约（L1：类型/必填/范围）
      ship-upon-pline.dmn              # 业务决策表（L2/L4：条件联动/状态机）
      ship-upon-pline.errors.yaml      # 错误码与提示资源
    inventory/
      count-order.schema.json
      count-order.dmn
    repack/
      box-repack.schema.json
  shared/
    error-codes.yaml                    # 全局错误码字典
    security-domains.yaml               # 参数安全域（硬编码边界）
  generated/                            # 构建产物，禁止手工编辑
    java/  ts/  sql/
4.2 规则声明语法（核心）
rule: WMS.OUT.PRODLINE_REQUIRED
enforcement: STRICT            # 编译期常量：STRICT / NORMAL / ADVISORY
when:                          # 触发条件（只读数据，不写逻辑）
  field: isShipUponPline
  op: eq
  value: 1
require: productionLine        # 必须非空的字段
params:                        # 唯一可配置部分，且必须在安全域内
  retry: { default: 3, min: 1, max: 5 }
code: WMS.OUT.PRODLINE_REQUIRED@v2
event: outbound.order.create   # 规则绑定的业务事件
version: 2                     # 规则版本，写入单据快照
owner: 仓储产品组               # 规则责任人
为什么 enforcement 是编译期常量：它不进配置中心、不进数据库、不开放 API。要修改它必须提 PR，CI 会检查 STRICT 规则的变更是否附带性质测试与影子发布报告。
4.3 参数安全域（硬编码边界）
# shared/security-domains.yaml —— 本身受代码评审保护，不热更新
qty.max:            { min: 1, max: 10000 }      # 单笔数量上限
batch.count.max:    { min: 1, max: 200 }        # 单箱批次数上限
rule.retry:         { min: 1, max: 5 }          # 校验重试次数
rule.timeout.ms:    { min: 50, max: 2000 }      # 单条规则超时
机制：配置中心写入参数时先查安全域，越界直接拒绝并告警。安全域是代码的一部分，改它要走 CI。这样"调阈值"自由，但"调到 0 或无限大"不可能。

WMS 强校验规则库（10 条实例）

真实场景

以雪花 WMS 入出库升级项目现有字段为例，把散落在代码里的强校验整理成规则清单。S=STRICT（不可配掉），N=NORMAL（可配参数）。

#场景规则条件 → 结果错误码级别版本
1下线即走-产线必填isShipUponPline=1 且 productionLine 为空 → 阻断OUT.PRODLINE_REQSv2
2下线即走-库位类型下线即走单入库库位类型 ≠「下线即走库位」→ 阻断OUT.LOCTYPE_MISMATCHSv1
3下线即走-库位状态下线即走库位状态必须为「待检」（不是冻结）→ 否则阻断OUT.LOCSTATUS_INVALIDSv1
4含瓶标记联动attribute6=1（含瓶）时 batchNo 必填 → 阻断INV.BATCH_REQSv1
5盘点数量上限实盘数 > 配置上限（安全域内）→ 警告并要求二次确认INV.QTY_EXCEEDNv2
6批次状态越库回传批次状态 ≠ 合格 时禁止回传 OC → 阻断INV.BATCHSTATUS_BLOCKSv1
7翻包箱码唯一性新箱码已存在 → 阻断（查库校验，走 L3 模板）RPK.BOX_DUPSv1
8拆组垛数量守恒拆后明细数量之和 ≠ 原垛数量 → 阻断DSY.QTY_MISMATCHSv1
9已过账单据作废单据状态=已过账 时禁止作废（状态机校验）→ 阻断DOC.POSTED_NOVOIDSv1
10库位编码格式不符合 ^K[0-9]{4}$ → 提示（前端体验校验，后端仍需重放）LOC.CODE_FORMATNv1
整理原则：先不要一次性把 10 条都迁移。第 1、2、7、8 条是库存安全底线，优先；第 5、10 条是体验类，最后做。每条规则迁移时补齐：契约声明、性质测试、错误码资源、影子发布报告——四件不齐不验收。

DMN 决策表：替代膨胀的 DSL

业务可读

下线即走的联动规则用决策表表达。业务人员能直接读表，命中哪一行一眼可见——这是 DSL 做不到的可解释性。

序isShipUponPlineattribute6库位类型结果
111（含瓶）下线即走库位通过，要求 productionLine + batchNo
210（净水）下线即走库位通过，要求 productionLine，不要求批号
31—其他库位阻断 OUT.LOCTYPE_MISMATCH
41——阻断 OUT.PRODLINE_REQ（产线为空时）
50——走普通出库规则集，不适用本表
规则命中可解释：校验失败时返回的不只是错误码，还有 decision: table#3（命中第 3 行）。排查"为什么被拦"不用猜条件组合。决策表按序匹配、命中即停，规则冲突在表内可见。
07

三道防线与影子发布

强制力保真

01编译期：没有开关可配

STRICT 规则的契约声明中没有 enabled 字段，生成产物中也不存在。关闭它的唯一途径是改源码、过 CI、发版本，提交记录与审批链天然留痕。阈值参数走配置中心，但必须落在安全域内。

02运行期：边界权威 + 影子发布

服务端 API 边界执行编译产物，带超时（50~2000ms 安全域）与查询行数配额，防止复杂规则拖垮接口。新规则上线前必须走影子模式：新旧规则并行，新规则只记录不拦截，采集一个完整业务周期后按算法判定是否放行。

03存储期：数据库硬约束兜底

NOT NULL、UNIQUE、外键、CHECK 不受任何配置影响。即便绕过边界校验（内部脚本、批量导入、数据修复），数据库仍拦得住。这是"强校验"真正的地基。
7.1 影子发布判定算法
  1. 新规则以 shadow 模式部署，双跑 ≥ 7 个自然日（覆盖一个完整盘点/出库周期）。
  2. 逐单计算四类结果：both-pass、both-reject、new-only-reject（新增拦截）、old-only-reject（新规则漏拦）。
  3. 门禁：new-only-reject / total > 0.5% 或 old-only-reject > 0 → 阻断发布，差异单据人工复核。
  4. 通过后切换 enforcer 版本；保留 30 天回滚窗口，预置回滚包。
  5. 上线后继续监控 7 天，命中率突变为 0 或飙升 3 倍触发告警。
为什么比双人审批更硬：审批只证明"有人同意过"，影子发布证明"在这套真实数据上没出事"。前者是流程证据，后者是数据证据。
08

性质测试与 CI 门禁

规则正确性

配置化最大的隐性成本是"规则本身写错了"。把规则写成可验证的性质，让 CI 穷举边界，而不是靠几条手写单测。

8.1 性质测试示例
// Rule as Property：对任意单据，该性质必须成立
[Property]
public void ShipUponPline_RequiresProductionLine(OutboundOrder order)
{
    Assume.That(order.IsShipUponPline == 1);
    order.ProductionLine = null;                 // 生成器随机构造其余字段
    var result = validator.Validate(order, version: 2);
    Assert.That(result.Errors, Has.Some.Matches<ValidationError>(
        e => e.Code == "WMS.OUT.PRODLINE_REQUIRED@v2"
          && e.Severity == Severity.Block));
}
8.2 CI 门禁流水线
  1. Schema 校验：契约文件语法合法、字段与 DDL 一致（自动比对列名/类型）。
  2. 性质测试：每条 STRICT 规则至少 1 条性质，生成器跑 ≥ 1000 组随机数据。
  3. 决策表完备性：检查条件组合是否有空洞（无规则命中）与冲突（多行同时命中）。
  4. 安全域校验：规则引用的参数必须声明在 security-domains.yaml 内。
  5. 错误码归属：每个 code 必须在资源表中有定义，禁止裸字符串。
  6. 变更门禁：STRICT 规则的 enforcement / when 变更，必须附影子发布报告，否则 CI 失败。
实测收益口径：不引用行业"提升 X%"的数字，建议用项目自身基线测量四个指标：规则变更平均交付时长、表单相关缺陷逃逸率、强校验绕过次数、零命中规则数。迁移前后各测一个完整迭代即可得出结论。

错误码与可观测契约

提示热更新

上一版的提示资源表解决"改文案不发版"；升级后它同时成为规则的观测入口和生命周期管理载体。

字段说明与示例
code全局唯一、带语义版本：WMS.OUT.PRODLINE_REQUIRED@v2，与规则版本联动，避免同码不同义
severityblock / warn / info；STRICT 规则只能是 block，CI 强制检查
i18n中文"下线即走时产线不能为空"、英文 "Production line is required"，支持 {field} 变量插值
channel.pda短文案 ≤ 20 字，适配 PDA 小屏
channel.pc完整文案 + 处理建议，适配 PC 端
owner规则责任人，零命中清理时自动通知
metrics命中率、拦截率、人工覆盖次数，按天打点；高频误报自动告警
 
# 规则产物只存错误码，不存文案
{ "field": "productionLine", "rule": "requiredWhen",
  "when": { "var": "isShipUponPline", "eq": 1 },
  "code": "WMS.OUT.PRODLINE_REQUIRED@v2",
  "decision": "ship-upon-pline.dmn#4" }

# 资源表独立热更新
WMS.OUT.PRODLINE_REQUIRED@v2:
  zh: "下线即走时产线不能为空"
  en: "Production line is required"
  pda: "产线必填"
  severity: block
  owner: 仓储产品组
不可越界的线：文案热更新可以秒级生效；"是否拦截"永远不热更新。这条边界要写进平台约定，并在 CI 中检查——资源表只能含 zh/en/pda/severity/owner 等展示字段，不得含 enabled 或 when。

阶段交付物验收标准参与角色风险

风险清单与 FAQ

落地障碍
风险表现缓解
决策表膨胀条件组合爆炸，表变得不可读拆成多个子决策表（按场景分表），命中即短路；单表不超过 20 行
契约与代码双写有人绕过契约在业务代码里补校验CI 静态扫描：禁止在业务层出现硬编码提示与校验分支；发现即失败
影子期误判新规则误拦正常业务未被发现差异单据强制人工复核；新增拦截率超阈值自动阻断；保留回滚包
性能退化复杂规则拖慢接口 P99编译产物 + 超时/行数配额；上线前压测，P99 超基线 20% 阻断
老数据误判新规则套到历史单据上事件版本绑定，单据快照记录规则版本；按版本解释历史数据
团队习惯阻力开发者觉得"改配置更快"明确三通道：文案随时改、参数审批改、强校验发版改；用 CI 固化
常见问题回答
改一句提示真的不用发版？是。文案在资源表热更新，秒级生效；但拦截行为不变——这是刻意设计的边界。
强校验能不能临时关掉？不能热关。只能切换产物版本（回滚包预置，30 分钟内可完成），且自动留痕。这正是设计目标。
和现有低代码平台冲突吗？不冲突。契约是低代码平台底层的规则层，UI 仍可用低代码搭建；只是强校验不再由页面配置决定。
DSL 还要不要？一般校验（ADVISORY）可保留轻量 DSL；STRICT 规则一律走 DMN + 编译产物，不允许写 DSL。
需要一次性全量迁移吗？不需要。按第 5 节优先级从 STRICT 规则开始，逐条迁移、逐条影子验证；存量代码与契约并存直到替换完成。
12

终极形态：让非法状态不可表示

再深一层

前 11 章再强，仍然有一个共同的隐含前提：先让数据进内存，再跑一遍校验决定拦不拦。终局是取消这个前提——用类型系统把业务规则写进数据结构本身，让"下线即走但产线为空"这类状态根本构造不出来。这时校验器不是被关掉，而是没有存在的必要。

层级做法非法数据在哪被挡校验器数量能否被配掉
L0 硬编码三端各自写 if运行期3 份能，且会漏改
L1 配置化规则中心 + DSL 解释运行期1 份解释器能，改配置即可
L2 编译期契约契约源码 + CI 物化构建期0 运行时开关不能，要走发版
L3 类型化不可表示类型系统 + 解析边界编译期 / 构造时0 校验器不存在可配的东西
一句话分水岭：L0~L2 是"数据可以是非法的，但我们检查它"；L3 是"非法数据在类型层面没有合法构造路径"。前者叫 validate，后者叫 parse。
12.1 Parse, don't validate：不变量从检查项变成构造前提
// 传统：任何 Order 都可能非法，每个函数都得先校验一遍
function ship(order: RawOrder) {
  if (order.isShipUponPline === 1 && !order.productionLine) throw ...
  if (order.locationType !== "SHIP_THROUGH") throw ...
  // 真正业务只有一行，校验占了半屏
}

// 终局：解析成功后得到的类型本身就携带不变量
type OutboundOrder =
  | { kind: "normal";         location: NormalLocation }
  | { kind: "shipUponPline";  productionLine: NonEmptyString;
      location: ShipThroughLocation };   // 错误组合没有对应分支

function parseOrder(raw: RawOrder): Result<OutboundOrder, ParseError> {
  // 唯一一次校验发生在系统边界，且返回的是新类型
}

function ship(order: OutboundOrder) {
  // 这里不可能拿到非法状态——想传错都编译不过
}
12.2 三个实现手段

01智能构造器（Smart Constructor）

构造函数私有，只暴露 Parse(raw) → Result<T, Error>。外部拿不到"未经验证的 T"，只能通过解析入口。类型一旦构造成功，全链路都不再校验。C# 用 record + 私有构造 + static Parse；TS 用 brand type 防止裸字符串冒充。

02判别联合 / 代数数据类型

把业务变体枚举进类型：normal 与 shipUponPline 是两个独立分支，各自携带自己才有的字段。想构造"下线即走但没产线"的对象，TypeScript 直接编译报错。这就是把第 5 节的 DMN 决策表编译进了类型系统——表里的非法组合没有对应的类型分支。

03数据库约束做最后兜底

类型只管应用内，绕过应用直连库仍可能写脏数据。库位类型/状态用枚举 CHECK，箱码用 UNIQUE，数量守恒用事务内断言。类型与约束表达的是同一份不变量，由同一份契约生成——不是重复校验代码，是重复表达。
12.3 哪些能消掉校验器，哪些不能
场景能否类型化说明
字段联动（产线必填）能判别联合让非法组合无对应类型分支，编译期挡住
状态机流转（已过账禁作废）能命令类型只接受特定状态的单据，作废方法对已过账单据不存在
枚举合法性（库位状态）能用封闭枚举替代字符串，非法值无法表示
数量守恒（拆组垛）部分可在解析时计算并构造带证明的值，但依赖输入完整性
查库唯一性（箱码重复）不能外部世界状态，类型系统看不到数据库——只能做"带副作用的解析"
外部输入（PDA / 接口报文）不能永远需要解析边界，把不可信数据转成类型化值
关键边界：类型化消灭的是系统内部的重复校验，不是消灭校验本身。系统边界（报文、PDA、数据库、外部系统）永远要有解析层——只是这层从"散落各处的 if"收敛成"一处 Parse"，且一次解析全链路受益。
12.4 代价与适用边界（诚实说）
  • 改造成本：存量代码从"裸 DTO + if"改成类型化模型，工作量不小。建议只在新模块（新单据、新接口）采用，老模块维持第 2 阶段的契约编译。
  • 表达力上限：跨库状态、时序、权限上下文无法完全类型化，这部分仍要靠边界权威执行 + DB 约束。
  • 跨语言难题：前后端语言不同，类型无法直接共享。做法是共享契约（Schema / DMN），各端从契约生成自己的类型——回到第 4 章的契约仓库，只是生成目标从"校验器"变成"类型定义"。
  • 团队门槛：需要开发者习惯"让非法状态无法表示"的建模方式，比写 if 门槛高。收益是长期维护成本骤降，适合核心域，不适合一次性脚本。
12.5 与前 11 章的关系：不是替代，是收敛
层次解决什么在架构中的位置
L1 配置化易变的体验类校验、提示文案配置中心，热更新
L2 编译期契约STRICT 规则、跨库查库、状态机契约仓库 + 构建期物化
L3 类型化核心单据的内部不变量领域模型 + 解析边界
三者叠加才最强：外部输入在解析边界转成类型化值 → 内部用类型保证不变量 → 边界权威执行剩余规则 → 存储用 DB 约束兜底。校验器数量从 3 份 → 1 份 → 0 份，不是靠"配得更聪明"，是靠"把规则挪到更早、更硬的地方"。
13

结论

更好的设计一句话：不是把校验做得"更会配置"，而是把强校验做成不可热改的契约编译产物——契约即校验、编译即强制、边界即唯一、事件即版本。

如果再问一次"还有更好的吗"，答案是终局那一步：让非法状态无法构造，让校验器彻底消失。L1 解决一致性，L2 解决强制力，L3 解决存在性——三层不是三选一，而是按场景逐层收敛。

四件齐备才算工程闭环：① 契约仓库统一规则与字段；② 编译期物化、运行期无开关；③ 边界权威执行 + DB 硬约束；④ 影子发布 + 性质测试 + 错误码可观测。缺任何一件，都会在不同程度上退回硬编码或退回不可控。
口径说明：本文为《配置化架构设计》（JSON Schema + DSL + 提示资源化 + 三端生成 + 三级管控）的升级版，不替代原方案，而是回答"强校验怎样从可配置走向不可配掉"。示例字段沿用雪花 WMS 下线即走场景（isShipUponPline / productionLine / attribute6）及盘点、翻包、拆组垛规则。收益口径建议以项目自身基线测量，不引用未经验证的行业数字。
