01

设计约定

适用范围与阅读方式

本文覆盖 WMS 10 个功能域、TMS 9 个功能域，共 19 个域。每个域按同一结构展开：功能点清单、Agent 操作矩阵、Tool 契约、数据与规则依赖、风险门禁、终局形态。前五项用于落地，最后一项用于校准投入方向——与总方案第四章"三个消亡"对齐，避免在当前项目里做终局注定要消失的精装修。

功能点清单描述"系统今天有什么"；Agent 操作矩阵描述"智能层叠加什么"；Tool 契约是二者的接口；依赖表说明前置条件；门禁表定义安全边界；终局形态说明该域在长期演进中的去向。

成熟度与风险分级

成熟度沿用 L0~L4 五级：L0 实时作业不 Agent 化，L1 只读问答，L2 带确认执行，L3 主动处置，L4 多 Agent 协同。风险分三级：只读（read-only）、一般写（write-normal）、高危（write-high）。风险级别决定门禁强度，与成熟度无关——一个 L2 操作可能是高危，一个 L3 操作可能只是只读巡检。

Tool 契约通用规范

每个 Tool 契约必须包含五个强制字段：名称（域.动作.对象）、风险级别、入参、出参、补偿路径。涉及写操作必须额外声明幂等键。所有数值以字符串传输，保留五位小数；所有枚举用大写下划线；未知入参一律忽略而非报错；超过 64KB 的出参截断并在响应中留痕。

数据中台返回的任何数字必须由 Tool 提供，不得由模型生成。Agent 回答中的每个数量、单号、时间都要能回溯到具体数据源，无法溯源的信息必须标注"未查到"，不允许推测填充。

统一数据口径

跨全部功能域复用以下口径：数量统一保留五位小数；时间统一用带时区的 ISO 8601；组织、仓库、货主构成权限三元组；库存事实以"库位加物料"为粒度，一期不拆批次、不拆物资状态；业务状态翻译统一走 LOV 编码，不在 Agent 侧硬编码中文枚举。

02

WMS 功能域详细设计

基础主数据

定位：所有作业规则的源头。Agent 在这里的价值不是"帮人填表"，而是把散落在多张配置表里的规则变成可问答、可校验的知识。

风险门禁

操作风险级别门禁要求补偿路径

终局形态：主数据域不会消亡，但会从"配置表"变成"业务本体的一部分"。终局里它不再是给人维护的后台页面，而是 Agent 理解业务语义的词典——物料、库位、产线的定义被写进本体，规则从配置项变成可被 Agent 推理的策略。当前该域的表格维护界面是负资产，字段语义与关系是资产。

04

跨域协同链路设计

单个域的工具封装完成后，真正的价值出现在跨域编排。本章给出三条关键链路，它们也是 L4 多 Agent 协同的落地形态。

主链路：出库到签收

链路环节为：出库单确认 → 运单生成 → 承运商选择与调度 → 月台预约协商 → 装车交接 → 在途跟踪 → 签收确认 → 回单归档。

WMS Agent 与 TMS Agent 之间必须交换结构化交接契约，不允许各自维护一份状态：

    "goodsReady": "已备货状态与数量",
    "dock": "月台编号",
    "readyTime": "可交接时间，ISO 8601",
    "sealNo": "封签号",
    "evidenceRefs": "[称重/照片/复核记录]"
  },
  "handoffToTms": {
    "waybillNo": "运单号",
    "carrier": "承运商与车牌",
    "driver": "司机与联系方式",
    "arrivalAtDock": "预计到达月台时间",
    "acceptance": "交接确认状态"
  },
  "arbitration": "当双方时间窗不一致时，以出库方 readyTime 为基线，由调度 Agent 提出改派方案，禁止任一方自行妥协"
}

异常闭环链路

链路环节为：异常发现（WMS 盘点差异 / TMS 在途异常） → 证据聚合 → 归因 → 分级处置 → 结果回写 → 策略沉淀。

关键设计是"策略沉淀"：每次人工纠偏都要转成可复用规则，写到策略库，下次同类异常由 Agent 直接给出建议。这是"决策资产化"的落地形态，也是系统越用越懂这个仓库的唯一途径。

异常分级处置规则：只读异常（如轻微时效偏差）Agent 自主记录并汇报；一般异常（如数量差异）出建议待人决策；高危异常（如库存过账错误、货损定责）强制人工处置，Agent 只负责取证。

以"把今天发往宁波方向的订单安排出库发运"为例，编排层按以下顺序调用工具：

域优先级矩阵

优先级按"Agent 价值密度 × 数据就绪度"排序，而非按业务重要性排序：

优先级功能域理由
P0报表与查询（WMS/TMS）、基础主数据、在途跟踪只读、数据相对齐备、可快速建立信任
P0接口与集成、异常处理（TMS）跨源归因价值最高，证据链数据已部分具备
P1入库管理、出库管理、库存管理、运力与承运商、运输订单写操作但流程稳定，可在确认门禁下安全落地
P1库内作业（差异归因与动态抽样部分）价值高但依赖盘点事务日志语义化

P3系统与权限（Agent 部分）权限对象是制度问题，需先厘清责任边界

前置数据条件

每个域的 Agent 化都有硬性前置条件，不满足时不该启动：

前置条件影响的域不达标后果
指标口径字典完整全部报表域数字不可信，禁止上线

与四期路线的映射

一期（只读助手）覆盖 P0 中的报表、主数据、在途查询；二期（辅助执行）覆盖 P1 的入库、出库、运力、运输订单；三期（主动 Agent）覆盖接口巡检、异常归因、盘点差异归因；四期（多 Agent 协同）覆盖调度、装车、签收的跨域编排。P2 中的费用结算与包装辅料视数据成熟度决定是否提前。

验收要点

单域验收清单模板

每个功能域交付前必须逐项通过以下检查：

检查项验收标准
功能点清单覆盖该域全部在产功能，无遗漏核心功能
工具契约每个写操作都有幂等键与补偿路径，风险级别已标注
数据来源每个输出字段可追溯到具体表与字段
权限过滤越权调用被拒绝，且不进入预览环节
门禁执行高危操作必须双人复核，无法绕过
数字可信所有数字来自工具返回，模型不生成数字
终局标注已写明该域终局形态，投入方向与之一致

通用验收项

跨全部域的硬约束：中文 Windows 环境下工具输出必须显式设置 UTF-8，避免 GBK 乱码；所有数量五位小数、可为负；时间带时区；超过 64KB 出参截断留痕；未知入参忽略；业务错误不计入可用性监控分母；429 是唯一允许的限流 4xx；幂等记录保留不少于 90 天。

终局对齐检查

每域验收时追加一问：本域本轮投入是"让旧结构跑得更好"，还是"让旧结构不再必要"？前者记为装修，后者记为资产。一个迭代周期内，资产类投入占比应不低于三成，否则说明设计偏离了总方案的终局方向。
