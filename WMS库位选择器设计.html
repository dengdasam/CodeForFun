库位选择器：数百个候选怎么选得快

仓储系统里「选库位」是个高频动作，几百个候选值，操作员可能戴着手套在 PDA 上点。本文给出分层收敛的交互模型，以及 Vue3 与 Kotlin + Compose 两套完整实现，逐条标注容易出错的地方。

Vue3 + TypeScript Kotlin + Jetpack Compose 扫码枪集成 PDA 适配 2026-11

核心结论：几百个库位的选择器，难点不在组件，而在怎么让操作员在 3 秒内选对。正确做法不是给一个更漂亮的下拉框，而是四段收敛——扫码优先、级联缩小、拼音搜索、最近使用置顶。只做一件事的话，做扫码：PDA 的扫码枪本身就是键盘，成本几乎为零，收益最大。

01先判断：你到底在解决什么问题

同一个需求，戴手套在 PDA 上点和坐电脑前用鼠标，是完全不同的两个问题。

使用形态核心矛盾方案重心
PDA / 手持机
（仓库现场）		 屏幕小、戴手套、必须快、边走边操作 扫码优先，列表只是兜底
PC 电脑
（办公室）		 可搜索、可多选、要精确、要批量 搜索 + 筛选 + 最近使用

大部分 WMS 两个都要。正确做法是一套数据模型，两套交互壳——不要试图用一个组件同时满足两种形态。

为什么普通下拉框会失败

<select> 或 el-select 在 300+ 项时会出现三个硬问题：

  • 移动端卡顿：iOS Safari 原生 picker 超过约 200 项就明显卡，安卓 WebView 更差。
  • 找不到：纯滚动找 A-03-05-02 这种编码，人眼扫描几乎不可能，滚动条拖半天还在 A 区。
  • 易错：相邻库位只差一位数字，点错了就是发错货——返工成本远超开发成本。
一句话：问题的正确提法不是「怎么让下拉框更好用」，而是「怎么把 300 个候选收敛到 20 个以内」。人的认知负荷在 20 项以内是可以一眼扫完的。

为什么级联有效

几百个库位分摊到「仓库 × 库区」后，每段往往只剩十几项。人不用滚动，直接点。

层级典型数量控件选择理由
仓库1 – 5按钮组（平铺）数量少，下拉反而多一次点击
库区5 – 15按钮组 / 分段控件可一屏展示完
库位10 – 30可见列表 + 搜索框不要用下拉，列表能一眼扫完并显示库存状态

搜索索引：一定要支持拼音首字母

操作员记不住 HBQR-03-05，但记得「华北区」。所以索引要同时覆盖四种输入：

输入方式示例命中逻辑
完整编码A-03-05-02精确匹配，排第一
编码前缀A-03前缀匹配
库位名称华北区3排名称包含
拼音首字母aq → A 区全部pinyin 前缀匹配
关键实现细节：拼音字段必须建库时算好存进数据库，不要在前端/客户端实时转换。
原因：实时转换需要引入拼音库、每次搜索都要遍历 300 条做转换，性能差且容易出错。

03Vue3 实现

Web 端（含 H5 移动端）的重点是扫码要依赖输入框焦点——这是这套方案最大的结构性弱点，后面会讲怎么缓解。

① 扫码优先

<!-- PDA 扫码枪原理：模拟键盘逐字符输入，末尾自动回车 -->
<!-- 所以不需要调摄像头，一个输入框就够了 -->
<input
  id="locInput"
  placeholder="扫库位码 / 输入编号"
  autocomplete="off"
  inputmode="none"        <!-- 关键：阻止软键盘弹出 -->
  @keyup.enter="onScan"
/>
function onScan(e) {
  const code = e.target.value.trim()
  if (!code) return

  // 第一优先：精确命中，直接完成
  const loc = findByCode(code)
  if (loc) { selectLocation(loc); return }

  // 第二优先：模糊，可能只扫到部分编码
  const hits = fuzzyFind(code)
  if (hits.length === 1) { selectLocation(hits[0]); return }
  if (hits.length > 1)  { showCandidates(hits) }   // 多结果才展示
  else { toast('未找到库位 ' + code) }
}
Web 方案的致命弱点：扫码依赖焦点。只要焦点丢失（弹出 dialog、操作员误点其他控件、页面重新渲染），扫码内容就会落入 null 或错误的输入框，操作员以为扫上了，实际没有。
缓解手段：页面挂 visibilitychange 和 click 监听，每次交互后重新给输入框 focus()；dialog 关闭后强制聚焦。但这些都是补丁，根治不了。这是原生方案的主要优势之一（见第 04 章）。

04Kotlin + Compose 实现

原生端最大的改进：扫码不依赖焦点。在 Activity 层拦截 dispatchKeyEvent，全局生效。

① 全局扫码拦截

class MainActivity : ComponentActivity() {

    private val scanBuffer = StringBuilder()
    private var lastKeyTime = 0L

    override fun dispatchKeyEvent(event: KeyEvent): Boolean {
        if (event.action == KeyEvent.ACTION_DOWN) {

            // 关键：超时清空。扫码枪逐字符输出，间隔约 10ms
            // 超过 200ms 无新按键 → 是人工输入或上次扫描中断，必须清缓冲
            if (System.currentTimeMillis() - lastKeyTime > 200) {
                scanBuffer.setLength(0)
            }

            when (val code = event.keyCode) {
                KeyEvent.KEYCODE_ENTER -> {
                    val barcode = scanBuffer.toString().trim()
                    scanBuffer.setLength(0)
                    if (barcode.isNotEmpty()) {
                        scanViewModel.onScanned(barcode)   // 交给 ViewModel
                        return true                        // 消费事件，别落入输入框
                    }
                }
                else -> {
                    val ch = event.unicodeChar.toChar()
                    if (ch.isLetterOrDigit() || ch == '-' || ch == '_') {
                        scanBuffer.append(ch)
                        lastKeyTime = System.currentTimeMillis()
                        return true
                    }
                }
            }
        }
        return super.dispatchKeyEvent(event)
    }
}
细节为什么重要
200 ms 超时清缓冲扫码枪若未配置回车后缀，或扫描中途被打断，脏数据会残留，导致下次扫码拼错
用 event.unicodeChar
而非 keyCode 映射		部分扫码枪输出非 Unicode 字符时 unicodeChar 返回 0，此时需退回 KeyCharacterMap
拦截后 return true阻止事件继续分发给子控件，否则内容会同时进入输入框造成重复
注意：全局拦截会吞掉人工键盘输入。纯 PDA 上没问题（通常无实体键盘）。若设备有实体键盘，需用 InputDevice.getVendorId()/getProductId() 识别扫码枪设备，只拦截该设备的事件。
但不要硬编码 VID/PID——部分扫码枪有多个 HID 接口（Keyboard + LED + Consumer Control），按接口描述符判断更稳。

② 数据模型

@Immutable
data class Location(
    val id: String,
    val code: String,        // A-03-05-02
    val name: String,        // A区3排5层2位
    val pinyin: String,      // aq3p5c2w  ← 建库时算好存库
    val zone: String,        // A
    val stock: Int = 0
)

@Immutable
data class Zone(
    val code: String,
    val name: String,
    val locationCount: Int   // 显示用，不加载全部明细
)
@Immutable 必须加，但只能加在真正不可变的类型上。Compose 把标准 List/Set/Map 视为不稳定（无法证明不可变），导致不必要的重组；而给可变数据乱加注解会造成 UI 不更新（Compose 认为没变化而跳过重组）。

③ 状态机

sealed interface LocationPickerState {
    // ① 扫码优先 —— 默认态，占满屏幕
    data object Scanning : LocationPickerState

    // ② 级联选择
    data class SelectingWarehouse(val list: List<Warehouse>) : LocationPickerState
    data class SelectingZone(val wh: Warehouse, val zones: List<Zone>) : LocationPickerState
    data class SelectingLocation(
        val wh: Warehouse, val zone: Zone,
        val locations: List<Location>
    ) : LocationPickerState

    // ③ 搜索结果
    data class Searching(val query: String, val results: List<Location>) : LocationPickerState

    // ④ 最近使用
    data class Recent(val list: List<Location>) : LocationPickerState
}

用 sealed interface 的好处：when 表达式编译期强制穷举，新增状态时所有渲染分支都会报错提醒，不会漏写。

④ ViewModel

class LocationViewModel(
    private val repo: LocationRepository,
    private val savedState: SavedStateHandle
) : ViewModel() {

    private val _state = MutableStateFlow<LocationPickerState>(LocationPickerState.Scanning)
    val state = _state.asStateFlow()

    private val _query = MutableStateFlow("")

    init {
        // 搜索防抖 300ms，避免每敲一个字都查库
        viewModelScope.launch {
            _query
                .debounce(300)
                .distinctUntilChanged()
                .collectLatest { q ->
                    if (q.length < 2) return@collectLatest
                    val hits = repo.search(q)
                    _state.value = LocationPickerState.Searching(q, hits)
                }
        }
    }

    /** 扫码枪回调入口 */
    fun onScanned(barcode: String) {
        viewModelScope.launch {
            val exact = repo.findByCode(barcode)
            when {
                exact != null -> confirm(exact)         // 精确命中，直接完成
                else -> {
                    val hits = repo.fuzzyFind(barcode)
                    when (hits.size) {
                        0 -> _state.value = LocationPickerState.Searching(barcode, emptyList())
                        1 -> confirm(hits.first())      // 唯一命中，自动选中
                        else -> _state.value = LocationPickerState.Searching(barcode, hits)
                    }
                }
            }
        }
    }

    private fun confirm(loc: Location) {
        repo.recordUsage(loc.id)                    // 记录使用频次
        savedState["picked"] = loc.code             // 进程被杀也能恢复
        _state.value = LocationPickerState.Scanning
    }
}

两个关键细节

  • debounce(300) + collectLatest：新查询到来时取消上一次，防止慢查询覆盖快查询结果
  • savedState["picked"]：PDA 在仓库里跑，系统回收进程很常见，保存选择结果恢复后不丢

常见错误

  • 用 collect 而非 collectLatest：会导致结果乱序
  • 不做防抖：每敲一个字符查一次库，输入卡顿
  • 只存 ViewModel 不存 SavedStateHandle：进程回收后选择丢失

⑦ 搜索：Room 里的排序策略

@Query("""
    SELECT * FROM location
    WHERE code LIKE '%' || :q || '%'
       OR name LIKE '%' || :q || '%'
       OR pinyin LIKE :q || '%'
    ORDER BY
      CASE WHEN code = :q THEN 0
           WHEN code LIKE :q || '%' THEN 1
           ELSE 2 END,
      usage_count DESC
    LIMIT 50
""")
suspend fun search(q: String): List<LocationEntity>

ORDER BY 里的 CASE 是关键：让精确匹配排最前、前缀匹配次之、其余最后。操作员输入 A-03 时，该看到的顺序符合直觉，而不是按数据库默认顺序。

06必踩的坑清单

① LazyColumn 的 key 必须是业务 id

不提供 key 时 Compose 默认用 index 作为 key。数据一变（搜索后重排），整个列表重建，滑动闪烁、动画失效。绝不要用 UUID.randomUUID()——那等于每次都是新 item。

② @Immutable 不能乱加

List 默认不稳定。给可变数据强加注解会导致 UI 不更新（Compose 认为没变化而跳过重组）。只有类型确实满足「所有可观察变化都会通知 Compose」这个契约才能标。

③ 扫码枪 VID/PID 不要硬编码

部分扫码枪含多个 HID 接口（Keyboard + LED + Consumer Control），硬编码会匹配失败。按接口描述符判断更稳，或直接不做设备识别、只靠超时机制区分人工输入。

④ 不要一次性拉全部库存

// ❌ 300 个库位带库存一起查 → 接口 1–2 秒
// ✅ 按库区/可见范围分段查 → 100 ms 内

⑤ 拼音字段不要运行时转换

实时转换要引拼音库、每次遍历全量数据，既慢又容易出错。建库时算好存字段，查询直接 LIKE。

⑥ PDA 上要防止屏幕熄灭

// 操作员戴手套端着货，屏幕灭了要重新唤醒，体验极差
DisposableEffect(Unit) {
    val activity = LocalContext.current as Activity
    activity.window.addFlags(WindowManager.LayoutParams.FLAG_KEEP_SCREEN_ON)
    onDispose { activity.window.clearFlags(WindowManager.LayoutParams.FLAG_KEEP_SCREEN_ON) }
}

07选型建议

要快、要稳、有 PDA → Kotlin + Compose。焦点无关的扫码、原生列表性能、进程恢复免费，这三点在仓库现场是硬需求。代价是仅限安卓，且需要 Android 工程环境。

要兼容 PC 和 H5、迭代频繁 → Vue3。一套代码覆盖办公室和手机浏览器，改完刷新即可验证。代价是扫码依赖焦点这个结构性弱点，只能靠补丁缓解。

你的情况建议
仓库现场用 PDA，操作员戴手套Kotlin + Compose（扫码焦点问题是决定性的）
办公室 PC 操作 + 偶尔手机查Vue3（PC/H5 一套覆盖）
两者都要一套数据模型，两套交互壳：PC 用 Vue3，PDA 用原生
只想先验证流程Vue3 做原型，跑通再决定要不要上原生
无论选哪个，先做扫码。如果只能实现一个功能：把扫码跑通。它覆盖 70–80% 的实际操作，实现成本最低（PDA 扫码枪本身就是键盘），收益最大。

技术依据：Android dispatchKeyEvent 扫码枪集成实践（多来源交叉验证：200 ms 超时清缓冲、unicodeChar 回退 KeyCharacterMap、多 HID 接口不硬编码 VID/PID）；Jetpack Compose LazyColumn 性能优化官方指南（稳定 key、contentType、@Immutable 契约、避免嵌套滚动）。

方案基于 Vue3 + TypeScript 与 Kotlin + Jetpack Compose 两套栈分别实现，代码为可运行片段而非伪代码。整理日期 2026-11-27。
