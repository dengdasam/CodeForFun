Lichess 技术架构拆解

网页 Scala SSR，移动端 Flutter，两套代码库。基于对 lichess.org/player/bots 原始 HTML、HTTP 响应头、mobile 仓库 pubspec.yaml 与官方 README 的交叉验证，逐条给出证据而不是凭印象判断。

Scala 3 / Liplay scalatags 服务端渲染 Snabbdom 前端 Flutter 3.50 / Dart 3.14 Riverpod 3 2026-11 实测

一句话结论：Lichess 最反直觉的地方不是技术选型，而是同产品三套栈、三份代码。网页走 Scala 服务端渲染 + 轻量虚拟 DOM（2245 个 bot 条目全在原始响应里），移动端走 Flutter 自绘 + Riverpod 状态管理 + 本地三款 Stockfish（安装包 237 MB）。没有追求统一技术栈，只有对每个平台约束的独立回答。

02实测证据：这是纯服务端渲染

是不是 SPA，最直接的判据是「关掉 JS，内容还在不在」。我抓了原始 HTML 直接数。

# 抓取原始 HTML
curl -sL https://lichess.org/player/bots -o bots.html
# → HTTP 200 | 378,307 字节

# 数 bot 条目是否在服务端 HTML 里
grep -c 'bots__list__entry' bots.html
→ 2245          # 2245 个条目，全部带 <a class="...">

# 文件特征
字符数 374,016  行数 7  # 压缩排版，全部内容挤在 7 行里
标题 <title>449 Online bots • lichess.org</title>

结论很明确：2245 个 bot 的名称、等级分、简介、Play 链接全部直出在响应体里，没有任何一个是 JS 动态注入的。连标题里的 "449 Online bots" 这个数字都是服务端算好拼进去的。

一个容易误判的坑：页面里搜 react 会命中 2 次，但看上下文是 bot 描述里的 Reaction time: ~0.2 seconds——英文单词 "Reaction"（反应时间），不是 React 框架。同理，压缩后的 JS 里也搜不到 snabbdom 字样（被 minify 了），这类判断只能靠官方文档而不是字符串匹配。

03安全策略做得很硬

这份页面的 CSP 是我近期见过最严格的之一。

<meta http-equiv="Content-Security-Policy" content="
  default-src 'self';
  script-src 'nonce-dY2SXKd24NmRS35nWGSbZNC2' 'self';
  connect-src 'self' blob: data: ws://*.lichess.org
               https://explorer.lichess.org https://tablebase.lichess.org;
  frame-src 'self' www.youtube.com player.twitch.tv player.vimeo.com;
  base-uri 'none';
  img-src 'self' blob: data: *;
">
  • 每请求一次性 nonce：内联脚本必须携带 nonce="dY2SXKd2..." 才能执行，攻击者注入的 <script> 因为没有 nonce 会被直接拦死。
  • base-uri 'none'：封死 <base> 标签劫持——这是 XSS 里很经典的一招，改了 base 之后所有相对路径都指向攻击者域名。
  • frame-src 白名单：只允许 YouTube / Twitch / Vimeo 嵌套，其余一律拒绝，防点击劫持。
  • x-frame-options: DENY：老式浏览器兜底，双重防护。
  • connect-src 精确到子域：WebSocket 只放行 ws://*.lichess.org，数据外泄通道被限死。

04前端是原生 ES Module，不是单文件 bundle

这点和很多大站不一样——它让浏览器自己并行拉模块，而不是打成一个巨型 bundle。

<script defer src="/assets/hashed/cash.min.cbb7928a.js">
<script type="module" src="/assets/compiled/manifest.c8f4caaa.js">
<script type="module" src="/assets/compiled/site.2JU5HNLY.js">
<script type="module" src="/assets/compiled/lib.4GDVGLWV.js">
... 共 20+ 个 lib.*.js 分块

// site.js 开头原样长这样
import{a as Ve,b as R,c as _e,d as W,f as ze}from"./lib.4GDVGLWV.js";
import{a as X}from"./lib.KAC4AIWV.js";
特征观察结果含义
模块加载方式type="module" + import/export浏览器原生 ESM，靠 HTTP/2 多路复用并发拉取

哈希命名site.2JU5HNLY.js / site.26a0b3a1.css内容哈希做缓存失效
构建产物结构manifest.js + assets/compiled/Vite 的典型输出布局
polyfillcash.min.js（defer）轻量 jQuery 替代，仅 1 个额外依赖
i18ni18n/site.en-GB.*.js语言包独立成模块，按需加载

05服务端架构：把实时通信拆出去

这是 Lichess 最值得借鉴的设计决策。

浏览器
HTTP 请求
Cloudflare
CDN / 防护
lila (Scala)
页面 + REST API
MongoDB
120 亿+ 对局
浏览器
WebSocket
lila-ws
独立进程
Redis
消息总线
lila
业务逻辑
  • 为什么拆？WebSocket 是长连接，几万人在线下棋会占满连接池。把它独立成 lila-ws 进程，主应用 lila 就能保持无状态、可水平扩展。
  • 怎么通信？两个进程通过 Redis 做消息总线，不直接 RPC 调用，解耦彻底。
  • 棋规为什么单独抽 scalachess？棋类规则是纯函数，抽成独立子模块后可以被服务端、客户端、分析工具共用一份实现，避免规则不一致。

06与「桌面壳 + SPA」路线的对比

拿之前分析过的皮卡鱼象棋（Tauri + Vue 3）作对照，两者几乎是镜像关系。

无 JS 可用性内容仍可读（渐进增强）完全不可用
SEO天然友好不适用
语言数量两套（Scala + TypeScript）两套但都是熟悉的（Rust + TS）

SSR 路线的收益

  • 首屏快：HTML 到手就有内容，不等 JS
  • SEO 天然友好，爬虫直接读
  • 渐进增强：JS 挂了核心内容还在
  • 前端体积小：Snabbdom 仅 3 KB
  • 无 hydration 成本（内容已存在）

SSR 路线的代价

  • 前后端两套语言，上下文切换成本
  • 模板逻辑与交互逻辑天然割裂
  • 页面内跳转体验不如 SPA 顺滑
  • 部分交互仍需前端补 JS
  • UI 改动要重编译，不能热更

为什么选 Flutter，而不是复用网页代码

  • 棋盘手感是硬需求：拖拽走子、premove（预走）、低延迟音效，这些在 WebView 里做体验很差。Flutter 直接自绘，延迟可控。
  • 引擎要跑在本地进程：Stockfish 是原生二进制，需要 FFI 桥接。Flutter 的 dart:ffi 可以直连，WebView 里做不到。
  • 离线能力：本地开局库、离线谜题、12 档人机对战，都需要真实的本地存储与文件系统权限。
  • 代价也很明显：网页端和 App 是两套完全独立的代码库（Scala+TS vs Dart），功能同步要靠人工对齐，无法共享组件。

状态管理：Riverpod 3

移动端的架构选择与网页端也完全不同——网页端靠服务端渲染，几乎不需要前端状态管理；移动端是纯客户端应用，状态管理成了核心。

棋盘与棋规：把网页的资产复用到 Dart

这是整个移动端最聪明的一点——两个纯 UI/规则库被移植成了 Dart 包，让 Flutter 客户端能直接吃下网页端的积累。

包版本定位
chessground11.1.0「为 lichess.org 开发的棋盘 UI，内部不含棋规，所以可用于各种变体」。原本是网页的 TypeScript 库，这里是 Dart 移植版
dartchess0.15.0棋规实现：走法生成、FEN 读写、PGN 读写，支持变体。对应网页端的 scalachess 角色
auto_size_text3.0.0文字自适应缩放，防止长用户名撑破布局
flutter_layout_grid2.0.8CSS Grid 式布局，贴近网页设计稿

命名哲学值得学：chessground 只画棋盘不管规则，dartchess 只管规则不管画面。两个包零耦合，所以换皮肤换规则互不影响。这与网页端把 scalachess 抽成独立子模块是同一个思路——只是这次跨了语言。

引擎：三款 Stockfish 打进 App

移动端的引擎方案比网页端复杂得多。网页端靠服务端集群算力，移动端必须自带。

FlavorNNUE 权重用途
light（默认）内嵌约 1 MBStockfish 19 + 精简网络，无需下载即可用，适合移动场景
latestNoNNUE需自行下载 .nnue完整强度版，启动评估前必须先有网络文件
variantFairy-Stockfish国际象棋变体引擎（Crazyhouse 等 8 种变体）
  • 每种 Flavor 同时只能有一个实例：create() 在同类引擎未 dispose 时会抛 StateError。但不同 Flavor 可以并行——所以能一边跑 NNUE 分析、一边跑 Fairy 变体对手。
  • 每个引擎占两个原生线程（一个跑引擎、一个读输出），不占用 Dart isolate，因此引擎运行中仍可热重载。
  • 通信走 UCI 文本协议：stockfish.stdin = 'go movetime 3000'，输出通过 Stream<String> 推送。这和桌面端皮卡鱼象棋的做法完全一致——引擎独立进程 + 文本协议是被反复验证的正确设计。
  • 另有 lc0（Leela Chess Zero，注明 "no GPU"）作为第二条引擎路线，以及 flutter_onnxruntime 支持 Maia（模仿人类失误风格）神经网络的人机对战。

一个值得记住的结论：同一个产品，三个平台、三套技术栈、三份代码。网页选 Scala SSR 求首屏与 SEO，移动端选 Flutter 求手感与离线，桌面选 Tauri 求体积。没有「统一技术栈」的执念，只有对每个平台约束的独立回答——这大概是 Lichess 最值得学的架构决策。

08可借鉴的三件事

  • 把长连接从主应用剥离：凡是「实时」与「请求响应」混在一起的服务，都该考虑拆成两个进程 + 消息总线。主应用保持无状态才好扩容。
  • 纯逻辑抽成独立模块：像 scalachess 那样把规则/算法单独抽出去，服务端、客户端、测试共用一份实现，永远不会有"两边规则不一致"这类 Bug。
  • CSP 用 nonce 而不是白名单：script-src 'nonce-xxx' 比列一堆域名更稳，攻击者注入的脚本根本拿不到 nonce。再配 base-uri 'none' 补掉 base 劫持这个常见缺口。
关于开源：Lichess 全部代码以 AGPL-3.0 开放（lichess-org/lila）。AGPL 的关键约束是——如果你修改后以网络服务形式提供给他人使用，也必须公开源码。想基于它二次开发成商业产品，需要先评估这条。
